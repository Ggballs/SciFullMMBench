# Query Generation

Given the paper title, abstract, and a literature-review-style summary of a scientific paper organized by views (`contribution`, `method/dataset`, `experiment/result`, `limitation/scope`), where each view contains a short narrative summary and indexed bullet points, generate **1-2 human-written-style general retrieval queries per view**.

The goal is to sound like a real researcher searching for a paper they partly remember / explore the new literature, not like a benchmark description, annotation guideline, or paper abstract.

## Primary Goal
Write queries that are:
1. **Human-like Natural**: natural, direct, but still academic, efficient, and research-oriented in phrasing
2. **Moderate Specific**: precise enough to identify the paper or a very small set of papers, but not so specific that it relies on exact numbers, rare phrases, or brittle details that sounds like LLM-generated query.
3. **Concise**: usually **12-20 words**, ideally around **14-17 words**
4. **Search-realistic**: something a person would actually type into a paper search engine
5. **Discriminative**: centered on the paper's most distinctive idea, setup, result, or limitation
6. **Beyond-abstract Retrieval Hook**: the query should not be solvable or trivially retrievable from the abstract alone; it should lean on details that are more specific than the abstract's top-line claims

## Human Style Requirements
### 1. Use human query templates
Use the following template families:
- **What/Which paper or method...**: about **50%**
- **Is there / Are there / Any papers/methods/datasets on/about/that...**: about **30%**
- **Give me / Show me / Provide / List / Find / Search for papers...**: about **20%*

### 2. Construct Query Focus
- Choose **ONLY ONE main retrieval hook** from the view: the most memorable and discriminative aspect, such as a distinctive method, unusual task, benchmark characteristic, key finding, limitation, or failure mode.
- You may add **one supporting qualifier** only if it helps narrow the search naturally.
- Do **not** stack multiple filters, exclusions, or result details into one query. If the query starts to sound like a paper abstract or a checklist of properties, simplify it.
- Each query should be grounded in **exactly one bullet point**: choose the single most discriminative bullet from the view and base the query on that bullet only.
- Use natural phrasing with modifiers such as `for`, `with`, `using`, `without`, `on`, and `about`.
- Prefer the **shortest natural query** that still preserves the core search intent.
- Avoid using only the paper abstract's generic topic, task, or headline claim as the retrieval hook.
- Prefer details that would help distinguish the paper **beyond what the abstract alone already makes obvious**, while still sounding like a realistic search query.
- If a query could be answered or matched well using only the abstract, make it more discriminative by shifting toward a more specific method detail, evaluation setup, limitation, trade-off, or notable finding from the bullet.


### 3. Prefer conceptual paraphrases over rare exact terms/statics
Prefer the kind of wording a person would remember, or topics a researcher would explore not the exact internal terminology / statics from bullet points.
- paraphrase **secondary/source dataset names** , **internal construction labels**, niche acronyms, and benchmark ingredients into functional descriptions
- keep a very famous top-level term only when removing it would make the query too generic

Good transformations:
- `MMMU-Pro` -> `a multimodal understanding dataset`, `COCO-based negation templates` -> `object-negation image templates`, `GPT-based search` -> `LLM-assisted search`

### 4. Sound like a real researcher
Queries should feel like tip-of-the-tongue search requests:
- mention the **core mechanism**, **task**, **setting**, **dataset type**, **finding**, or **limitation**
- keep only the most memorable details
- use domain terms naturally
- use a question mark for question-style queries

Each query should focus on the **few details most likely to help retrieval**.

## Multimodal Bonus Rule
If a view contains bullet points referencing specific tables, figures, or equations,
generate **1 additional queries** for that view.

For these bonus queries:
- do **not** describe the figure/table in exhaustive detail, do not mention the figure/table in the query, but use the figure/table as a clue to identify a distinctive aspect of the paper that can be expressed in a natural query form (in justification, explain the figure/table clue and how it inspired the query)


##Good Query Examples:
"What is the first paper that uses the generalized linear model to analyze multi-neural spike train data?"
"Is there a paper that utilizes the characteristics of human evolutionary knowledge to guide language models in generating scientific ideas?"
Give me papers which show that using a smaller dataset in large language model pre-training can result in better models than using bigger datasets.

## Output Format
Output a JSON object with views as keys:

```json
{{
  "contribution": [
    {{
      "query_text": "generated query text",
      "is_multimodal": true/false (whether the query is inspired by a specific figure/table/equation/... non-textual element in the paper. Be RIGOROUS!),
      "related_bullet_indice": 1,
      "related_bullet_justification": "1-2 sentences justifying whether the query relates to the bullet and why it is a good retrieval hook"
    }},
  ],
  "method/dataset": [],
  "experiment/result": [],
  "limitation/scope": []
}}
```

Return valid JSON only. Do not add explanations before or after the JSON.
