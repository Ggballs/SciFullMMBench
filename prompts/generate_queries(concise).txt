# Query Generation

Given a consolidated bullet-point summary of one scientific paper by views
(`contribution`, `method/dataset`, `experiment/result`, `limitation/scope`), generate
**1 human-written retrieval query per view by default**.

Only generate a 2nd query for a view when there is a clearly different retrieval hook
or when multimodal figure/table/equation clues justify it.

Goal: sound like a real researcher searching for a partly remembered paper, not like a
benchmark card, annotation guideline, or abstract rewrite.

## Output Goals

Each query should be:

1. **Human-like**: natural academic search phrasing
2. **Specific**: narrow enough to retrieve this paper (or very few)
3. **Concise**: usually **12-20 tokens** (ideal ~14-18)
4. **Search-realistic**: something a person would actually type into a paper search engine
5. **Discriminative**: centered on distinctive mechanism/task/result/limitation

## Analyzer-Compatible Openings

Start every query with one of these openings:

- `Which paper...`
- `Which method...`
- `What paper...`
- `What method...`
- `What dataset...`
- `What is...`
- `Is there a paper/method/dataset/study that...`
- `Are there any papers on/about/that...`
- `Any papers on/about...`
- `Give me papers on/about/that...`
- `Show me papers on/about...`
- `Provide papers on...`
- `List papers on...`
- `Find papers on...`
- `Search for papers on...`
- `Can you find papers that...`
- `Can we find papers on...`

Opening strictness (important):

- The first words must exactly match one opening pattern above.
- Do not use near-miss starts such as `Which benchmark...`, `Which study...`,
  `Are there papers where...`, `What benchmark...`, `Which dataset benchmark...`.
- If using `Which ...`, the second word should be `paper` or `method`.
- If using `What ...`, prefer `paper`, `method`, `dataset`, or `is`.

Target mix across all queries for one paper:

- `What/Which ...`: about **40%**
- `Is there / Are there / Any papers ...`: about **27%**
- `Give/Show/Provide/List/Find/Search ...`: about **21%**
- `Can you / Can we ...`: about **3%**

Diversity rules:

- do not start every query the same way
- if total queries >= 4, use at least 2 template families
- if total queries >= 6, use at least 3 template families

## Hard Constraints

- Keep each query to one main retrieval hook + at most 0-2 natural constraints.
- Avoid clause-heavy, inventory-like phrasing.
- Prefer **no number** unless truly retrieval-critical.
- If numbers help, use coarse language: `a few hundred`, `around a thousand`, `large-scale`.
- Avoid exact or shorthand counts (`1,536`, `1.5k`, `14k`, `3M`) unless essential.
- Avoid combining counts with administrative policy details (e.g., split/release terms).
- Prefer conceptual paraphrases over copied internal names/acronyms from source bullets.
- Keep exact paper/method/dataset names only when they are the strongest retrieval anchor.
- Avoid source ingredient names/acronyms like `MMMU-Pro`, `PIN-14M`, `COCO-based ...`
  unless they are truly necessary to retrieve the target paper.

## Style Guidance

Write like tip-of-the-tongue search:

- mention memorable mechanism, task setting, dataset property, result, or limitation
- keep wording direct and compact
- use domain terminology naturally
- use `?` for question-style queries

Avoid:

- summary tone (`this paper introduces...`, `the authors propose...`)
- marketing tone (`novel`, `state-of-the-art`, `breakthrough`)
- conversational filler (`please`, `thanks`)
- metadata-heavy benchmark inventory language

## Good vs Bad

Good:

- `Is there a multimodal retrieval benchmark with contradiction-based negatives?`
- `What paper studies test-time training for LLMs?`
- `Which multimodal retrieval benchmark has expert queries and no training split?`
- `Are there evaluation-only multimodal retrieval benchmarks with expert queries and no training split?`

Bad:

- `Identify the benchmark that defines three retrieval families, uses GPT-based search, expert verification, interleaved documents, and multiple negative construction pipelines.`
- `Are there any evaluation-only multimodal retrieval benchmarks with 1,536 expert queries but no training split?`

## Content Selection

For each query, pick one memorable retrieval hook from the view:

- distinctive method/model design
- unusual task formulation
- dataset/benchmark characteristic
- striking empirical finding
- limitation/failure mode/scope boundary

Do:

- preserve functional meaning
- vary emphasis across views

Do not:

- copy rare source names/acronyms by default
- pack multiple independent facts into one query
- produce overly generic queries that match many unrelated papers
- use opening forms outside the approved opening list

## Multimodal Bonus Rule

If a view includes figure/table/equation clues, generate **2 extra queries** for that view:

- prepend `(multimodal)` to those query texts
- keep them concise and human-like
- reference the clue naturally, without exhaustive detail

## Final Checklist

Before output, verify each query:

- starts with an approved opening
- opening matches the approved pattern exactly (no near-miss variants)
- stays around 12-20 tokens
- is human-like and retrieval-realistic
- avoids exact count-heavy metadata phrasing unless essential
- avoids source-ingredient names/acronyms unless retrieval-critical
- is distinct from other queries for the same paper

## Output Format

Output JSON only:

```json
{{
  "contribution": [
    {{"query_text": "Is there a method that achieves X without using Y?", "is_multimodal": false}},
    {{"query_text": "(multimodal) What paper has a figure comparing X and Y?", "is_multimodal": true}}
  ],
  "method/dataset": [],
  "experiment/result": [],
  "limitation/scope": []
}}
```

Return valid JSON only. No extra text.
